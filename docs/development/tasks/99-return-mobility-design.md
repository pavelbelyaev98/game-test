# Task 99 - Compare return mobility and a placed teleporter

Type: design/research; documentation only. Status: `planned`. Prerequisites: `100`/`101` user observations, complete production trip `15` and `70`'s initial navigation comparison. Actual paid `47` tiers supply later evidence rather than an additional entry gate. Pricing must be compatible with `98`'s decision or the current free-refill baseline.

Feature: [return and rescue](../../features/backlog/return-rescue.md). Context: [user's Meltopia comparison](../../research/player-idea-assessment.md), [risk register](../design-risks.md). The reported boredom concerns Meltopia, not this build. Normal physical return remains the baseline until a specific replacement/exception is selected.

Priority: revisit after the complete production trip `15` and `70`'s initial navigation comparison. Current `100`/`101` can still identify an actual problem early; fix demonstrated defects under their owners, but do not make an optional teleporter proposal a prerequisite for core equipment/content delivery.

## Comparison to prepare

- Test whether comparable horizontal friction occurs here, separating surface station distance, known lateral underground retracing, wrong turns, collision friction and movement feel. Record route/save, trip reason, vertical/horizontal/station portions and any segment the player wanted to skip. Preserve enjoyable ascent; an absence of a demonstrated problem is a valid reason to retain current travel.
- Propose matched-route comparisons: existing walk/sprint/flight; a tighter surface checkpoint where relevant; and a bounded change to horizontal movement/jetpack control where the route warrants it. Current planar speed is the same in air and on ground. Protect immediate stopping, crouch precision, readable aim and comfort; do not add an uncontrolled dash, camera kick or mandatory platforming.
- Compare a placed reusable anchor paired with the base against the best physical-travel option. Define whether it skips return, outbound retracing or both, and whether that removes the vertical travel the user enjoys. A teleporter is not automatically the recommended fix for a surface-layout problem.
- Prepare alternatives with **one primary limiter each**: cooldown, credits per use, or finite uses before replenishment. Show two successive full-bag trips, an early retreat and an empty-bag revisit. Diagnose waiting at an endpoint, rationing anxiety and costs replacing upgrades; do not stack all three limits by default or count forced cooldown waiting as useful pressure.
- For any recommended teleporter, specify endpoint count, placement/removal/retrieval, moving the work face, range/visibility/support, obstructed destination, carried loot, battery state, exact payment timing and save/load. Failed travel cannot spend a charge/fee or leave the player in solid terrain. No duplicated loot, cooldown reset on reload, undeclared account service or unexplored-destination teleport.
- Show consequences for jetpack/capacity purchases, return warnings, refill pricing and rescue use at poor/rich and early/late states. Preserve an ordinary finishable route without required teleport purchases; unresolved effects must be returned to `56`/`98`/`59` with a concrete example.

## Review and acceptance

Present the measured cause, recommended remedy and short action/route diagrams with tradeoffs. Review whether physical mobility alone solves the complaint, which trip segment may be skipped, and one chosen limiter if a teleporter remains worthwhile.

Record selected/deferred/omitted options, rationale and a before/after feel test in the return feature. If selected, create the next numbered implementation task with its save, invalid-action, economy and Windows review criteria; update the concept's physical-return exception explicitly. No asset, teleport, speed change or revised fee is implemented by this design.

# Task 35 - Persist excavation and progression across quit/reload

Type: implementation. Status: `done`. Prerequisites: 34 (complete). [Completion](../completed/35-save-load.md).

Feature: [core loop](../../features/backlog/core-loop.md). [Queue](../tasks.md). [Research basis](../../research/player-review-findings.md).

## Task contract

- Result: terrain, collected identities, inventory, wallet and owned shovel levels now persist together. This implements the locked rule that excavation never resets and provides the save boundary for [permanent discoveries (`36`)](../../features/backlog/buried-upgrades.md).
- Scope after `34`: persist the authoritative excavation density and deterministic generation state, discovery identities/collected state, carried records, wallet, owned upgrades, battery and player return position as one consistent save. Rebuild derived meshes/colliders and exposure from restored state before play resumes; developer overrides are not progression.
- Use versioned saves and atomic replacement with last-valid recovery. Failed/interrupted writes or incompatible data must not silently overwrite progress or start a fresh excavation; provide a readable recovery state. Autosave dirty state periodically, checkpoint after each successful sale/purchase and save on normal exit. Choose and measure a short maximum dirty interval; coalesce writes without losing changes made during a save, avoid full-grid work every frame and keep ordinary saving feedback quiet. Make automatic saving and failures understandable in the existing Pause/exit/recovery flow; no unexplained save station or repeated saving popups.
- Acceptance: dig downward and sideways, collect/sell/upgrade, return/rescue, quit and relaunch the Windows build. Restore the same traversable cuts, cleared remnants, absent collected finds and exact economy/upgrade state without duplication or a fresh seed. Force interruption during active digging and after sale/purchase, including during snapshot capture/replacement; restore the last complete terrain/discovery/economy snapshot atomically, with no duplicated sale or mixed revisions. Measure and document the maximum lost dirty interval and accepted transaction checkpoint timing. Check repeated load and unreadable saves; new reward state in `36` must use this same save boundary.
- Excavation never resets within a save through ordinary gameplay, rescue, reload or the ending. A separate new game and the existing explicitly confirmed development-only reset do not redefine that rule; preserve the release gate in `22`.
- Research basis: [persistent-investment findings](../../research/player-review-findings.md#persistent-investment) require durable player excavation. The implemented ownership boundary is recorded in [architecture](../../architecture.md). Version 1 uses bounded, checksummed compressed snapshots, a flushed pending file, same-directory replacement and a retained prior checkpoint: [.NET File.Replace](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=net-9.0), [FileStream.Flush](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=netframework-4.8.1). [Unity wantsToQuit](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Application-wantsToQuit.html) defers normal exit until the latest write; [persistentDataPath](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Application-persistentDataPath.html) keeps progress outside replaceable build files.
- User question: none required for the existing scoped save/recovery contract. Choose conservative technical defaults; propose any destructive save conversion or new player-facing save-management policy before adopting it. Future content/upgrades/photos/ending/achievements extend this boundary in their own tasks, without a forced fresh save.

## Accepted implementation and evidence

- Dirty state checkpoints every 10 seconds plus frame/writer latency; trades/rescue queue immediate whole-world checkpoints. One worker coalesces requests; terrain is copied only when changed. Loading reconstructs meshes/colliders in frame slices before Resume. Native and Editor profiles are separate.
- All 142 distinct checks pass (77 EditMode, 65 PlayMode, including the focused eight-test UI rerun). Coverage includes exact terrain/seed/identity/economy restoration, repeated loads, collision clearance, rescue, coalesced writes, four interrupted commit stages, profile locking, damaged/unsupported data and failed-write retry. Official CLI inspection verified Pause, recovery and failure presentation.
- Native Windows review collected/sold two finds for 19 credits, purchased shovel 2 for 10, then force-stopped/relaunched after transactions and during held digging. Restored terrain hashes, collected identities, charge and owned progression matched the last complete checkpoint; rescue and Save and quit preserved the excavation.
- Current 3,613,153-sample grid: healthy continuous digging reached 10.005 seconds dirty at capture, then 129-134 ms to completed checkpoint (observed loss window about 10.14 seconds). Transaction checkpoints completed in 106-127 ms during overlapping cuts. Changed-grid capture normally took 4-5 ms and copied 14.45 MB; cached captures took 0.08-0.24 ms with no density copy. ProfilerRecorder measured 14.475 MB versus 22 KB total capture-frame allocation. These are this machine's measurements, not universal bounds.
- Local evidence: `unity/Logs/Task35/` contains test results, Editor/native screenshots, checkpoint comparisons, performance samples and build report. Windows build succeeded at `2026-09-08 18:47 UTC`; validation-only profiles were archived there, leaving the user's first launch fresh. Larger/late-game save and edit budgets remain with `63`/`54`.
